# ADR-018 — архив аналитики: дневные снапшоты в приватном репо

- Дата: 2026-09-19
- Статус: **accepted**
- Связанные: `supabase/migration-026-analytics-daily.sql`, `ops/analytics/`, ADR-016 (тот же VDS и крон)

## Контекст

Вопрос владельца: «не только health check проводить, но и сохранять данные для аналитики…
у нас некоторые данные там живут месяц, некоторые 3. Хотелось бы всё-таки хранить минимум
несколько лет, чтобы можно было динамику анализировать».

Воронка живёт в таблицах с TTL: `jobs` — 30 дней (`src/lib/storage/cleanup.ts`),
`download_events` — 90, `page_views` — 30 (`src/lib/storage/retention.ts`). `payments` и
`feedback` не чистятся. Через месяц ответить «как менялась конверсия регистрация→оплата
за полгода» уже нельзя: сырых строк нет.

`/api/admin/analytics` считает почти все нужные метрики, но авторизуется токеном
залогиненного админа, отдаёт сырые данные с email и ничего не сохраняет.

Основной репозиторий публичный, поэтому бизнес-данные в него класть нельзя.

## Решение

1. **Дневной агрегат за UTC-сутки.** `src/lib/analytics/` считает снапшот: регистрации,
   задачи (статусы, типы работ, реферреры-хосты), скачивания, платежи (initiated/completed/
   failed, выручка, hook vs direct, медиана часов от регистрации до оплаты), CSAT и
   накопительные итоги на конец дня. Без email, `user_id` и `job_id`. Дни старше TTL
   получают `null` в соответствующих полях и имя таблицы в `partial` — чтобы пропуск
   нельзя было спутать с нулём.
2. **Два хранилища.** `analytics_daily(day PK, data jsonb, updated_at)` в Supabase (RLS без
   политик, только service_role) — для запросов из кода; приватный репозиторий
   `diplox-analytics` с `daily/YYYY-MM-DD.json` — для истории, диффов и работы Claude.
3. **Кто пишет.** `GET /api/cron/analytics-snapshot?date=` (auth как у остальных кронов:
   `CRON_SECRET`) делает upsert и возвращает JSON; крон на VDS `30 0 * * *` кладёт ответ
   в клон репозитория и коммитит, если есть diff. Бэкфилл за всю историю — локальный
   `scripts/analytics/backfill-daily.ts` на той же библиотеке.
4. **Недельный разбор.** Claude-routine в репозитории `diplox-analytics` раз в неделю
   пишет `reports/YYYY-Www.md` и открывает issue при аномалиях в оплатах или регистрациях
   (`ops/analytics/routine-prompt.md`).

## Последствия

- Динамика хранится годами при стоимости ~2 КБ в день. Повторный запуск за тот же день
  идемпотентен (upsert по `day`, один файл на день).
- Снапшот необратим: восстановить сырые строки из агрегата нельзя. Новую метрику за
  прошлые дни можно добавить только пока данные ещё в пределах TTL.
- Логика метрик продублирована с `/api/admin/analytics`. Роут оставлен как есть;
  объединять — отдельной задачей, если понадобится.
- `jobs.work_type` и `jobs.requirements_mode` есть в проде, но отсутствуют в tracked-миграциях
  (schema drift, обнаружен при разборе). Снапшот их читает; при пересоздании базы с нуля
  по миграциям эти поля отвалятся.
