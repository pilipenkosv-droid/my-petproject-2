# ADR-015 — ночной конвейер блога: разведка → редактор → автор → публикация

- Дата: 2026-09-18
- Статус: **proposed** — ждёт OK Сергея на реализацию
- Связанные: `vault/.claude/skills/blog-publisher-bot/` (устаревшая инструкция ручного процесса — не источник промптов для нового конвейера, правила текста переносятся выборочно, без упоминаний бота), `POST /api/blog/publish`

## Контекст

Старый процесс публикации — агент Claude Code по SKILL.md правил статические файлы `src/lib/blog/posts-*.ts`, гонял `npm run build` и `git push`. Последняя статья вышла 15.06.2026, в день удаления старого VDS — с тех пор блог не пополняется. Сайчас 110 статей ГОСТ-кластера и 79 статей кластера бота лежат статически; часть кластера бота уже читается из Supabase `blog_posts`. Сайт умеет принимать статьи через `POST /api/blog/publish` (Bearer-токен, Zod-схема, upsert в `blog_posts`, ревалидация `/blog` и sitemap) без пересборки — этим путём и пойдёт новый конвейер. Источники частотников и конкурентов либо не собираются вовсе (конкуренты, Wordstat), либо собираются вручную (Wordstat — март 2026, устарел); стратегия в `vault/knowledge/diplox-blog-strategy.md` тоже устарела.

Продукта «Diplox Telegram-бот» не существует — его не покупали, и он полностью убран с сайта. Новый конвейер не создаёт статей о нём и не упоминает его: этап 2 работает только с кластером `gost`, этап 4 отдельно проверяет текст на упоминания (см. ниже).

## Решение

### Архитектура: 4 этапа за один ночной запуск

1. **Разведка** (`recon.py`, без LLM) — обновляет данные о частотниках, конкурентах и собственных статьях.
2. **Редактор** (`score.py` + `editor.py`, 1 вызов LLM) — детерминированный скоринг тем → шорт-лист → один запрос модели, который выбирает тему и формирует бриф для автора.
3. **Автор** (`writer.py`, 1 вызов LLM) — пишет статью по брифу.
4. **Проверка и публикация** (`publish.py`, без LLM) — валидирует текст, при необходимости просит автора переписать один раз, публикует через `/api/blog/publish`.

Запуск — cron `0 2 * * *` UTC на сервере Timeweb, через существующий `/opt/diplox-cron.sh`. Lock-файл не даёт двум запускам пересечься. В Telegram ничего не отправляется — бот с этим конвейером не связан.

### Источники и свежесть

| Источник | Что даёт | Периодичность | Если недоступен |
|---|---|---|---|
| RSS/sitemap сайта | список опубликованных статей, slug/title/keywords | каждую ночь | конвейер не запускается без этого источника |
| Google Suggest (`scripts/google-suggest.ts`, публичный, без ключа) | подсказки по seed-фразам | каждую ночь | пропуск, пишется в лог |
| Google Search Console API (`~/.config/indexing-api/service-account.json`) | показы/клики/CTR/позиции своих статей | каждую ночь, если файл сервис-аккаунта есть на сервере | этап помечает «нет данных GSC», конвейер продолжает без него |
| Конкуренты (Kampus.ai, Study24.ai, Studgen — sitemap/RSS трёх сайтов) | заголовки чужих статей | раз в неделю | пропуск текущей ночи, данные недельной давности остаются в базе |
| Wordstat | частотность фраз | нет автосбора; используется ручной импорт `docs/wordstat-raw-data.json` как `source=manual`, пока нет API-токена | — |

Лимит времени этапа разведки — 60 секунд; сетевые ошибки отдельных источников не валят ночь целиком.

### Хранение: SQLite на сервере

Путь `/var/lib/diplox-blog/blog.db`. Объём небольшой (~200 статей, ~2000 фраз) — TF-IDF по заголовкам/ключевикам на чистом Python закрывает похожесть тем без внешних зависимостей. Эмбеддинги через Vercel AI Gateway (`voyage/voyage-4-lite`) — опциональный второй шаг, включается, когда на сервере появится ключ шлюза; вектора хранятся в той же SQLite, поиск косинусом в памяти. `sqlite-vec` не нужен, пока объём не вырастет на порядок.

| Таблица | Поля |
|---|---|
| `posts` | slug, cluster, title, description, keywords, date_published, source=site |
| `queries` | phrase, source (suggest / gsc / wordstat / manual), volume, impressions, clicks, ctr, position, seen_at |
| `competitor_posts` | site, url, title, seen_at |
| `topics` | id, cluster, seed_phrase, status (new / covered / rejected), covered_by_slug |
| `embeddings` | kind (post / query / topic), ref_id, model, vector (blob), updated_at |
| `briefs` | run_id, topic_id, json, model |
| `runs` | date, stage timings, llm_calls, tokens, cost_usd, result, published_slug, error |

### Конфигурация и секреты

Код — репозиторий `ops/blog-nightly/` (`recon.py`, `score.py`, `editor.py`, `writer.py`, `publish.py`, `db.py`, `llm.py`, `config.toml`), на сервере разворачивается в `/opt/diplox-blog/`. Логи — `/var/log/diplox-blog/YYYY-MM-DD.log`. Секреты — `/etc/diplox-blog.env`: `CROMINM_API_KEY`, `BLOG_PUBLISH_TOKEN`, опционально `GSC_SERVICE_ACCOUNT_JSON`, `AI_GATEWAY_API_KEY`.

### Этап 1 — разведка (recon.py)

Вход: seed-фразы из `topics`, список статей сайта, список конкурентов. Выход: обновлённые `queries`, `competitor_posts`, `posts` (свежий срез с сайта). Без LLM.

### Этап 2 — редактор (score.py + editor.py)

`score.py` (без LLM) строит шорт-лист из 10 кандидатов-тем по формуле: спрос (показы GSC, наличие в подсказках Suggest, частотность Wordstat/manual) × непокрытость (максимальная TF-IDF-похожесть на существующие статьи ниже порога) × сезонность (календарь сдач). Кандидаты берутся только из кластера `gost` — кластер бота (`second-brain`) исключён из генерации полностью, очереди «ГОСТ/бот по кругу» больше нет. Новые кластеры про оформление и подготовку работ без продукта-бота — возможное расширение `topics` позже, отдельным решением владельца.

`editor.py` — один вызов LLM со строгой JSON-схемой на выходе:

```
{
  "topic": str, "cluster": "gost",
  "target_query": str, "keywords": [5-7 str],
  "intent": str, "must_cover": [str],
  "internal_links": [str],   // только существующие slug из posts
  "avoid": [str],            // похожие статьи, которые нельзя пересказывать
  "gost_whitelist": [str],
  "tone": str
}
```

Бриф сохраняется в `briefs`.

### Этап 3 — автор (writer.py)

Один вызов LLM по брифу, выход — JSON `{title, slug, description, keywords, content_markdown}`. Модель задаётся параметром `writer.model` в `config.toml`, по умолчанию `gemini-3.7-flash-medium`; альтернатива — `deepseek-v4-flash` (для неё `max_tokens ≥ 6000`, в промпте явный запрет на рассуждения — у deepseek они входят в лимит токенов). Правила текста — файл `prompts/writer.md` (часть переносится из SKILL.md выборочно, сама инструкция устарела и не используется как источник целиком): обращение на «ты», 800–1500 слов, заголовки `##`, ГОСТы только из белого списка брифа, без выдуманных цифр, 1–2 внутренние ссылки. Явный запрет в промпте: продукта «Diplox-бот» не существует, упоминать его нельзя ни при каких условиях; продукт, о котором идёт речь, — сайт diplox.online с форматированием по ГОСТ и методичкам вуза.

### Этап 4 — проверка и публикация (publish.py)

Проверки без LLM: ≥600 слов; ≥3 ключевых слова из брифа, все встречаются в тексте; ГОСТы только из `gost_whitelist`; текст не содержит стоп-слов (`sergey|vault|second.brain|token|password|api.key`); slug уникален относительно `posts`; похожесть заголовка на существующие статьи ниже порога.

Отдельная проверка на упоминание несуществующего продукта: регулярка `бот|bot|телеграм|telegram|second brain|второй мозг` (без учёта регистра) по `title`, `description`, `content_markdown`, `keywords`. Совпадение → отказ без повторной попытки автора (в отличие от остальных проверок), причина в `runs` — `banned_product_mention`.

Провал прочих проверок → одна повторная попытка автора с перечнем замечаний. Повторный провал → отказ, запись в `runs` (без публикации, без Telegram-уведомления). Успех → `POST /api/blog/publish` сразу, без обложки (решение Сергея — публикуем сразу, без черновика); `topics.status = covered`; запись в `runs`.

### Правка сайта: ГОСТ-кластер тоже читать из БД

Сейчас ГОСТ-кластер отдаётся статически из `posts-gost.ts`, а `fetchSecondBrainPosts()` в `posts-db.ts` не фильтрует по `cluster`. Правка: бэкфилл `posts-gost.ts` → `blog_posts` с `cluster='gost'`; добавить `fetchGostPosts()` с фильтром по кластеру; `fetchSecondBrainPosts()` получает фильтр `cluster='second-brain'`; `posts.ts` берёт оба кластера из БД, статические массивы остаются как резерв на случай сбоя БД.

## Последствия

**Стоимость.** ≤3 вызова LLM за ночь (редактор, автор, одна переписка при провале), ~10–15 тыс. токенов ≈ $0,01–0,02 номинала Crominm ≈ 10–15 копеек по курсу покупки ($30 за 208,8 ₽). Один прогон — 2–3 минуты, память ≤200 МБ.

**Риски.**
- Crominm — серый провайдер без SLA; при 3 ошибках подряд ночь пропускается, конвейер не повторяет попытку до следующей ночи, событие пишется в `runs`.
- `gemini-3.7-flash` / `deepseek-v4-flash` — быстрые модели, не топ по качеству письма; модель — параметр конфига, можно сменить без переписывания кода.
- Публикация без черновика: статья видна сразу после успешного прогона проверки. Откат — удалить строку в `blog_posts` (ручная операция, скрипта пока нет).
- Полагание на Google Suggest без ключа — endpoint публичный, но неофициальный; может измениться формат ответа без предупреждения.

## План внедрения

Шаги по 1–3 часа:

1. Бэкфилл `posts-gost.ts` в `blog_posts` + правка `fetchGostPosts`/`fetchSecondBrainPosts`/`posts.ts`.
2. `db.py` (схема SQLite) + `recon.py` (сайт, Suggest, GSC — если файл сервис-аккаунта уже на сервере).
3. `score.py` (скоринг и шорт-лист тем, без LLM).
4. `editor.py` + `writer.py` + `prompts/writer.md` (правила текста и запрет на упоминание бота — заново, SKILL.md как источник не используется).
5. `publish.py` (проверки, повтор, вызов `/api/blog/publish`) + `llm.py` (обёртка над Crominm).
6. Деплой на сервер (`/opt/diplox-blog/`), `.env`, крон-запись через `/opt/diplox-cron.sh`.
7. Первая ночь в режиме `--dry-run` (все этапы кроме публикации, результат — бриф и черновик статьи в `runs`, без записи в `blog_posts`).

## Что нужно от Сергея

- Положить `CROMINM_API_KEY` и `BLOG_PUBLISH_TOKEN` в `/etc/diplox-blog.env` на сервере.
- По желанию: файл сервис-аккаунта GSC (`~/.config/indexing-api/service-account.json` → скопировать на сервер) и ключ AI Gateway — без них конвейер работает, просто без этих источников/без эмбеддингов.
- OK на первую реальную публикацию (после успешного `--dry-run`).

**Открытый вопрос, вне рамок этого ADR:** что делать с 79 уже опубликованными статьями кластера бота (статика `posts-second-brain.ts` + строки в `blog_posts`) — они описывают несуществующий продукт. Варианты: снять с публикации, переписать без упоминаний бота, оставить как есть. Решение за Сергеем, конвейер их не трогает.

## Как проверить

```bash
# сухой прогон — все этапы, без публикации и без записи в blog_posts
python3 /opt/diplox-blog/run.py --dry-run

# журнал последних прогонов
sqlite3 /var/lib/diplox-blog/blog.db "select date, result, published_slug, cost_usd from runs order by date desc limit 5;"

# бриф, который редактор передал автору в конкретном прогоне
sqlite3 /var/lib/diplox-blog/blog.db "select json from briefs where run_id = '<run_id>';"

# лог ночи
cat /var/log/diplox-blog/$(date +%F).log
```
